# mimalloc v3.7.1 on Graviton5

The baseline pins mimalloc v3.7.0 (`1ed67b5156a763441d2ec3c20221a7b3cd866129`). The candidate pins v3.7.1 (`1c842769cd1ef35f044f659804806505b58f0b48`). Both sides use the same `Cargo.lock`, Rust allocator implementation, features and benchmark source. The Graviton5 measurements used Linux AArch64 with THP set to `never`.

## Measurement plan

- Reuse the [v3.7.0 experiment](20261121-mimalloc-v3.7.0.md) with Rust 1.99.1, Clang and LLD 19.1.7, the Cargo `bench` profile, default features and `-C target-cpu=native`. Shuffle `.text*` at final link with seeds `11`, `22`, `33`, `44`, `55` and `66`. Compile both sides before acquiring the CPU.
- Measure elapsed time per 64 allocations and frees in `alloc_free_batch` on one warm thread at all nine sizes, comparing both versions via `MiMalloc`. Compare `mi_malloc_aligned(size, 8)` with `mi_malloc(size)` within each version. Use `alloc_then_free` to check single-pair latency and disassemble `mi_malloc` and `mi_free` to check paired loads and stores. The latter is a code generation check.
- Use one available isolated CPU and hold its `flock` lock throughout the measurement. Pin all threads to that single CPU and disable ASLR per process with `setarch -R`. Record CPU0 utilization, system load and competing tasks on the measurement CPU. Repeat a full block after verified external interference.
- Run the unchanged-code layout pairs `11/22`, `33/44` and `55/66` on the 8, 48, 1024 and 4096-byte `MiMalloc` batches and the 48-byte allocate/free pair. For each version comparison run ABAB for odd blocks and BABA for even blocks, restarting the process each time. Run Criterion 0.8.2 with 0.25 s warm-up, 0.75 s measurement, 25 samples and 10,000 resamples. The previous experiment took about 16 minutes.
- Read each run's median time from `new/estimates.json`. Use the median of two paired effects in each layout and report the median and observed range across layouts. Treat 2% as the minimum meaningful difference. A near-boundary result or comparable unchanged-code variation leaves the decision open. A single host does not establish cross-platform equivalence of the two allocation entry points.

## Results

On Graviton5 with Clang, the median `MiMalloc` batch time fell by 6.27% at 24 bytes, 6.58% at 64 bytes, 6.77% at 256 bytes, and 3.39% at 640 bytes. The reductions exceeded 2% in all six layouts at those sizes. The 8, 48, 224, 1024, and 4096-byte results had at least one layout below that threshold. Single allocate/free times changed by at most 0.06% in the paired median.

Keep the `MiMalloc` fast path. At 64 bytes, the candidate's `mi_malloc_aligned(size, 8)` took 3.91% longer than `mi_malloc` in the median, with a 2.12% to 5.40% overhead in all six layouts. At 48 bytes and 4 KiB, the median overhead was 4.32% and 3.48%. At 256 bytes the median overhead moved from 5.45% to −0.40% and the observed range crossed zero. At 1 KiB it fell from 3.18% to 1.49%, below the 2% threshold.

The six release comparisons and first three unchanged-code blocks took 15 minutes and 43 seconds on one isolated core. In 940 one-second samples, the housekeeping core reached 4.00% busy, the measurement core recorded no steal time, and the other isolated cores were idle. No competing runnable processes were observed on the measurement core. The one-minute system load ranged from 0.94 to 6.72 across all blocks and from 0.94 to 2.59 during the release comparisons.

`Cargo.lock` SHA-256 is `c6f781cba9c47b9e65a951192a696581e2fa4340ad4d44f2064984db5b4d0eeb` and `bench/benches/alloc.rs` SHA-256 is `a49f23aabb6046f093d23801afa565644019b5295bc2e4dcd043228e22c91cf9` on both versions. The kernel was `6.12.117+deb13-cloud-arm64`. The raw evidence records executable hashes, timestamps, CPU samples, and run order.

### Unchanged-code controls

Each column compares two links of v3.7.0. In the first pass, some 48-byte and 1 KiB batch runs had higher times while the single-pair latency remained stable. No competing process or CPU steal was observed, and the cause is unknown. We repeated all three blocks on the same core. The housekeeping core reached 2.02% busy in 72 samples, and no competing task was observed on the measurement core. The repeat did not reproduce the spikes. The 48-byte release effect is close to the variation in the repeated controls. All six 1 KiB release comparisons favored v3.7.1, but one layout fell below 2% and the first control pass showed larger variation than the median release effect. The 8-byte and 4 KiB effects are also comparable to control variation.

## Verification

Linux AArch64 glibc passed the Rust tests with default, `debug`, and `no_thp` features, release `override`, the C shared-library and `dlopen` probes, the release LSE variant, and the upstream C suites in default, debug, and secure builds. The guarded debug stress runs recorded nonzero sample counts. QSBR passed 52 checks with page retention disabled. QEMU 10.0.13 with `-cpu cortex-a72` passed the default release and upstream C suites. The upstream macOS-only `stress_pprof` case skipped on Linux. Nightly fmt, Clippy, and rustdoc checks passed. Libclang 19.1.7 reproduced the bindings, and all 216 bound functions were linkable.

Both versions built with `secure,no_thp` set the process THP disable flag by default. Starting the process with `MIMALLOC_ALLOW_THP=2` left the process THP disable flag clear in both versions. `MIMALLOC_SHOW_ERRORS=1` took effect in secure mode on v3.7.1, and both versions ignored `MIMALLOC_PAGE_FULL_RETAIN=-1` in secure mode. The host kernel's `never` policy limited the THP check to option handling and the process flag. THP use and native benchmark results on macOS and Linux x86_64 remain unmeasured.

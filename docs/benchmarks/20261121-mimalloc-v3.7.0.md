# mimalloc v3.7.0 on Graviton5

Baseline is the parent workspace at `6c282428b460c04150f1d01c476a57788380a5df` with mimalloc v3.6.1 (`56dc5eb80145f9a3ba7ca23d47c6a248b9d8586c`). The candidate updates mimalloc to v3.7.0 (`1ed67b5156a763441d2ec3c20221a7b3cd866129`). Both builds use the same `Cargo.lock`, allocator wrapper and benchmark code. The workspace changes to the wrapper are documentation only.

## Measurement plan

- Measure elapsed time per batch of 64 allocations and frees on one warm thread using the existing `alloc` bench. Compare the two versions using `MiMalloc`, and compare `mi_malloc_aligned(size, 8)` with `mi_malloc(size)` on the given versions. Keep all nine existing sizes. Track `alloc_then_free` separately to expose fast-path forwarding effects. Allocation alignment is checked by the existing bench and the workspace tests.
- Build natively with Rust 1.99.1, Clang and LLD 19.1.7, the Cargo `bench` profile, default features, and `-C target-cpu=native`. Pass LLD `--shuffle-sections=.text*=SEED` at final link for seeds `11`, `22`, `33`, `44`, `55`, and `66`. Compile both sides before acquiring a measurement CPU.
- Use one available isolated CPU and hold its `flock` lock through the session. A one-CPU affinity mask binds every thread to that CPU. Disable ASLR with `setarch -R`. Capture system load, CPU0 utilization and competing tasks on the measurement CPU. Repeat a full block after a verified interference event.
- For the unchanged-code comparison, use the three layout pairs `11/22`, `33/44` and `55/66`. Run each pair of builds in two adjacent pairs with alternating first side. Use the 8, 48, 1024 and 4096-byte `MiMalloc` batches as controls and include the 48-byte allocate/free pair. The release comparison runs four fresh processes per seed, with order ABAB for odd blocks and BABA for even blocks. Use Criterion 0.8.2 with 0.25 s warm-up, 0.75 s measurement, 25 samples and 10,000 resamples per case. Expected measurement time is about 14 minutes, plus repeats for interference.
- Use Criterion `new/estimates.json` median point estimates in ns. Each layout contributes the median of its two paired effects. Report the median and observed range across layouts. A 2% effect is the minimum for a performance decision. The unchanged-code controls are a limited layout/noise check. An inconclusive interval or comparable unchanged-code variation leaves the corresponding decision open. This run covers one Linux AArch64 machine and cannot determine whether the wrapper can drop its fast path across all supported targets.

## Results

On the Graviton5 with Clang, the paired median `MiMalloc` batch time dropped 5.51% at 1024 bytes and 5.76% at 4096 bytes, and rose 5.14% at 8 bytes. All six layouts showed those directions. The 4096-byte and 8-byte effects exceeded the corresponding unchanged-code ranges. At 1024 bytes the versions were separated in all six layouts, with a larger median shift than the unchanged-code comparison. The smallest shifts overlapped in magnitude. At 24 bytes the times rose in all six layouts, with a median of 5.46% and one effect below 2%. The other sizes had smaller or less consistent changes.

`mi_malloc_aligned` with alignment 8 remained slower than `mi_malloc` at 256 and 1024 bytes in all six v3.7.0 layouts, with median costs of 7.59% and 3.17%. At 4096 bytes the median overhead narrowed from 13.44% to 2.41%. Some smaller sizes showed effects in both directions. Keep the `MiMalloc` fast path. The results on this host cover Clang, alignment 8 and steady-state tests only.

The six release comparisons and all three unchanged-code blocks took 15 minutes and 39 seconds on one isolated core. The housekeeping core was at most 6.06% busy in 936 one-second samples. The measurement core recorded no steal time and the other isolated cores were idle. The one-minute system load ranged from 0.92 to 2.88 across all blocks and from 0.92 to 1.55 during the release comparisons. No competing runnable process was observed on the measurement core. An initial attempt was stopped and excluded because the CPU observer did not start.

`Cargo.lock` SHA-256 is `f9b631ecfe5efde82782ed27d217cee98927edc8d3b76ab34d202bf9334e14cd`. `bench/benches/alloc.rs` SHA-256 is `a49f23aabb6046f093d23801afa565644019b5295bc2e4dcd043228e22c91cf9`. The raw results also record all executable hashes, timestamps, CPU observations and run order. Rust 1.99.1 used LLVM 23.1.1. The kernel was `6.12.117+deb13-cloud-arm64`.

## Verification and evidence

Linux AArch64 glibc passed the default and release Rust tests, all nine CI feature combinations, release override, the C shared-library and `dlopen` probes, upstream C suites with default, `debug` and `secure`, and the LSE variant. The GNU Cortex-A72 runner (QEMU 10.0.13) passed the default release and upstream C suites. The MSRV, nightly fmt, Clippy and rustdoc checks passed. Libclang 19.1.7 reproduced the bindings, and all 213 bound functions were present. The secure C suite passed six protection checks and skipped the three per-page guard checks that require `MI_SECURE=5`. The QSBR no-retention run passed 52 checks. The standalone environment probe confirmed that secure mode ignores `MIMALLOC_PAGE_FULL_RETAIN`, still reads `MIMALLOC_ALLOW_THP`, and accepts a programmatic `mi_option_set` for page retention.
